# PROJECT.MD 공통 입력 계약

각 저장소의 기본 브랜치 루트에 `PROJECT.MD`를 두고 프로젝트 내용의 원본으로 관리합니다. 파일명과 위치, 마크다운 문서를 원본으로 사용한다는 점만 공통 계약으로 둡니다. 필수 항목·제목·목차·front matter·문서 작성 도구·생성 방식을 요구하지 않습니다. 내용과 문서 생성 방식은 각 프로젝트에서 결정합니다.

프로젝트 내용이 달라지면 해당 저장소의 `PROJECT.MD`를 갱신합니다. AI는 문서에 기반해 설명을 다듬거나 소개를 생성하는 보조 역할을 수행할 수 있으며, 원본 문서 관리의 소유자는 각 저장소입니다. Hub가 PROJECT.MD 원본을 자동으로 되쓰지 않습니다. 공통 관리 지침은 별도의 온보딩 PR로 제안합니다.

## Hub 입력 경계

`src/project-document/read-document.ts`의 `readProjectDocument`는 이미 확정한 기본 브랜치 HEAD SHA로 문서를 한 번 읽고 다음 정보를 반환합니다.

- `source`: 저장소 ID·경로·기본 브랜치·HEAD SHA·문서 blob SHA·문서 경로를 전달합니다.
- `markdown`: 문서 본문을 자유 형식 문자열로 전달합니다.

문서 형식의 의미를 파싱하거나 구조를 검증하지 않습니다. UTF-8 텍스트 읽기와 파일별 256 KiB 상한은 기존 수집 자원 제한에 맞춥니다. 문서가 없으면 `PROJECT_DOCUMENT_MISSING`, 읽을 수 없으면 `PROJECT_DOCUMENT_UNREADABLE`, 크기 상한을 넘으면 `PROJECT_DOCUMENT_TOO_LARGE`를 반환합니다. README를 대체 원본으로 사용하지 않으며 원문 GitHub 오류는 노출하지 않습니다.

입력 모듈은 본문을 출력하거나 저장하지 않습니다. 호출자는 비공개 문서와 승인 전 초안을 공개 로그·동기화 상태에 기록하지 않아야 합니다. 조회 실패 시 원본 저장소와 기존 프로젝트를 변경하지 않습니다.

문서 수집 자체의 범위는 입력 계약과 조회 경계까지입니다. 별도로 AGENTS.md 관리 지침의 온보딩 PR을 지원합니다. 기존 수집 워크플로는 유지하며 AI 실행, API 요청·응답, Hub 서비스 인증, 문서 반영 상태는 portfolio-api의 별도 작업과 연결해 구성합니다. 문서 조회 성공을 프로젝트 생성·반영 성공으로 해석하지 않습니다.

## 각 저장소 AGENTS.md에 적용할 지침

공통 지침의 실행 원본은 [`src/project-document/guidance.ts`](../src/project-document/guidance.ts)의 `PROJECT_GUIDANCE`입니다. 지침을 바꾸면 다음 스캔에서 새 버전의 온보딩 PR을 제안합니다. 문서의 내용 템플릿이 아니라 문서·이미지의 소유권과 유지 규칙입니다.

- 각 저장소는 루트 `PROJECT.MD`를 초안 작업에서 만들고 프로젝트 내용 변경 시 갱신합니다. 문서 구조와 작성 방법은 자유입니다.
- 각 저장소는 루트 `PROJECT.png`를 대표 이미지로 준비합니다. 배포된 웹서비스 화면을 우선 사용하고 화면이 없으면 생성형 썸네일을 만듭니다. 필요한 경우 해당 저장소에서 갱신하며 일반 변경마다 재생성하지 않습니다.
- 생성 도구를 사용할 수 없으면 미완료 사실을 알립니다. 지침 PR 머지는 문서·이미지 생성 완료가 아닙니다.
- 공개 가능한 소개와 이미지만 준비합니다. 지침은 비공개 정보 공개 권한을 부여하지 않으며 공개 이미지 업로드·URL 구성은 별도 반영 단계입니다.

## 자동 온보딩 PR

쓰기용 App을 설정하면 수집 시마다 이미 확정한 HEAD SHA로 루트 `AGENTS.md`를 확인합니다. 수집 SHA가 같아 본문 수집을 건너뛰어도 지침 점검은 실행합니다. 지침 점검은 임의의 소스 파일이나 실행 가능한 코드를 읽거나 실행하지 않습니다.

`AGENTS.md`가 없으면 생성하고 있으면 원문 뒤에 Hub 전용 구간을 제안합니다. 기존 관리 구간이 있으면 그 구간만 교체하고 나머지 내용은 그대로 보존합니다. 이전부터 동등한 지침이 있더라도 표식이 없으면 자동으로 의미를 판단하지 않으므로 PR에서 중복·충돌 여부를 검토합니다. 깨지거나 중복된 표식, 심볼릭 링크, 비 UTF-8 또는 64 KiB 초과 문서는 안전하게 실패합니다.

- `portfolio-hub/project-guidance-<지침 해시>` 브랜치와 기본 브랜치 대상 PR을 생성합니다. 기본 브랜치를 직접 수정하거나 자동 머지하지 않습니다.
- 이전 버전까지 포함해 열린 온보딩 PR이 있으면 새 PR을 만들거나 기존 PR을 덮어쓰지 않습니다. 기존 PR을 먼저 검토합니다.
- 같은 버전의 닫힌 PR이 있으면 재생성하지 않습니다. 거절·삭제 의사를 존중하며 재적용은 담당자가 기존 PR을 다시 열거나 수동으로 반영합니다.
- PR 생성 직전에 중단됐으면 부모 SHA와 전체 제안 트리가 일치하는 기존 브랜치를 재사용합니다. 일치하지 않으면 덮어쓰지 않고 실패합니다. 담당자가 해당 브랜치/PR을 확인한 뒤 수동 복구해야 합니다.
- archived·fork 저장소는 온보딩 쓰기를 건너뜁니다. 빈 저장소는 기존 수집 정책에 따라 재확인하며 커밋을 임의로 초기화하지 않습니다.

지침은 중앙에서 관리하지만 각 저장소의 지침 충돌을 자동으로 판정하지는 않습니다. 담당자가 PR을 확인하고 직접 머지합니다. 문서·이미지 생성은 이후 해당 저장소에서 도구를 사용할 수 있는 AI 작업이 수행합니다.

온보딩 결과는 `onboarding.created/pending/closed/current/skipped/failed` 집계만 출력하며 문서 본문·비공개 저장소 이름·PR URL·원문 오류는 출력하지 않습니다. 수집 성공 SHA와 온보딩 성공은 분리하며 온보딩 오류로 이미 성공한 수집 체크포인트를 되돌리지 않습니다. 실패한 저장소 뒤의 저장소도 처리한 뒤 집계 실패가 있으면 종료 코드 1을 반환합니다. 온보딩 실패를 기존 수집 실패 이력에 섞지 않습니다.

## 쓰기용 GitHub App 설정

수집 App은 계속 `Metadata: read`, `Contents: read`를 사용합니다. Hub 상태 저장은 기존 `GITHUB_TOKEN`을 유지합니다. 원본 저장소 PR 생성에는 별도 App을 조직에 설치하고 대상 저장소에 다음 권한을 허용합니다.

- `Metadata: read`
- `Contents: write`
- `Pull requests: write`

Hub 저장소 Actions에 다음을 설정합니다.

- Variable `HUB_ONBOARDING_APP_CLIENT_ID`: 별도 쓰기용 App의 client ID입니다.
- Secret `HUB_ONBOARDING_APP_PRIVATE_KEY`: 별도 쓰기용 App의 private key입니다.
- Variable `HUB_ONBOARDING_ENABLED=true`: 설정 완료 후 자동 온보딩을 활성화합니다.

워크플로는 별도 설치 토큰을 발급해 `HUB_ONBOARDING_TOKEN`으로 전달합니다. 기존 수집 토큰을 쓰기용으로 승격하지 않습니다. 비활성화 상태에서는 기존 수집만 실행하고 비활성 사실을 표시합니다. 활성화 후 토큰 발급/설정이 빠지면 실패하며 조용히 생략하지 않습니다. 로컬 실행은 `HUB_ONBOARDING_ENABLED=true`와 `HUB_ONBOARDING_TOKEN`을 비밀 설정으로 주입합니다. 실제 App 설치·권한 설정·워크플로 배포 전에는 조직 저장소에 PR이 만들어지지 않습니다.
